Artifact Description
The Travlr full-stack web application, which I initially developed during CS 465 Full Stack Development, is the artifact I chose for the software design and engineering category. Travlr employs an Angular administration interface, MongoDB with Mongoose for persistent trip data, and Node.js and Express for the server and REST API. Trip records can be created, updated, and deleted using the application's protected administrative functions, which also enable trip information to be obtained via the API. I chose this item because it shows how a software system's frontend, backend, database, routing, authentication, and application configuration all operate together. 

Rationale for Inclusion and Improvement
Since Travlr exhibits multiple software engineering abilities in a single functional solution, it is suitable for my ePortfolio. Although RESTful routes, database models, controller logic, and JWT-based authentication were already included in the original application, my code evaluation found ways to enhance security, validation, error handling, maintainability, and configuration. I modified the application to get the secret from an environment variable and eliminated the hard-coded JWT secret from the authentication setup as part of the improvement. I built a.env.example file for safe setup guidance, implemented a startup check that stops the application from executing when JWT_SECRET is not provided, added dotenv configuration, and secured the.env file using.gitignore. To record the Node.js version required by the improved project, I additionally created a.nvmrc file. Additionally, I enhanced the trip controller by incorporating reusable server-side validation for necessary trip fields prior to processing create or edit actions. A clear HTTP 400 response indicating missing mandatory fields is now sent to invalid input. Additionally, I implemented centralized API error handling, which means that while the standard website still uses its HTML error page, calls made under /api receive JSON error answers. To ensure that the website pictures are served properly, I fixed the static asset structure and eliminated redundant router declarations from the application settings. These modifications improve the project's security, predictability, maintainability, and ease of configuration for another developer.


Course Results and Success Indicators
The improvement offers compelling evidence in support of the course objective, which calls for the application of solid methods, abilities, and resources to apply computing solutions that provide value. Instead of replacing an already-existing full-stack application, I changed it, found flaws through code review, and made specific changes without compromising the functionality. By verifying each necessary trip field and rejecting incomplete data before it reaches the database operation, the validation procedure also illustrates programming logic. This directly supports the success indicator for software logic problem-solving programming solutions. Additionally, the work shows advancement toward the course end that is security focused. The original application's usage of a hard-coded JWT secret was a significant design error. The improved application provides a safe example configuration, shifts that value outside of the source code, stops the private environment file from being included in source control, and fails at startup if the necessary secret is missing. 
I confirmed that HTTP 401 Unauthorized is returned when a request is made to establish a trip without authentication. I purposefully submitted an empty trip after authenticating with a test account, and I confirmed that the new validation returned HTTP 400 Bad Request along with the list of missing information. Following the modifications, tests were conducted on the standard website, the travel page, the photos, the MongoDB trip data, the GET /api/trips endpoint, and the missing-trip response. These tests show that the security and design enhancements are effective without impairing the functionality of the current application. 
Thoughts on the Process of Enhancement
Improving Travlr reaffirmed that adding more features is not the only way to make a program better. I had to think about how the program was impacted by modifications to the configuration, dependencies, authentication, routing, controllers, database access, and static files. Getting the previous project to function in the current development environment was one of the challenges. Before the project could function properly, an updated version of Node.js and further dependent setup were needed. Images that were kept in the public directory of the Angular application but not accessible from the root Express public directory constituted another problem. The entire website presentation was restored by adjusting the static asset placement. 
While it emphasized the distinction between code that looks correct and an improvement that can be shown to be functional, the testing process was particularly beneficial. Prior to testing API behavior, authorization, and incorrect input independently, I evaluated normal site behavior. The application was enforcing the intended restrictions, as evidenced by the protected POST request return 401 and the authenticated empty request return 400. My comprehension of secure configuration, defensive validation, API error handling, dependency management, and preserving current functionality while reworking a full-stack application has all enhanced because of this improvement. The final product more accurately reflects the security attitude and software engineering techniques I wish to showcase in my ePortfolio.
